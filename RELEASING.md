# Releasing

## Versioning

[Semantic Versioning](https://semver.org/), derived from the Conventional Commit types since the last tag:

| Commits since last tag | Bump |
|---|---|
| any `!` or `BREAKING CHANGE:` footer | major |
| any `feat:` | minor |
| anything else | patch |

For this repository a breaking change means a breaking *schema* change: a removed or renamed field, a changed field number or type, a renamed enum value, or a changed RPC signature.
`make breaking` runs on every pull request and is what normally stops these from landing by accident.

`Cargo.toml` and `pom.xml` carry the same version, and the tree between releases sits at the version that was last released.
The release commit bumps both to the new number, and that merged commit is what gets tagged.

## Cutting a release

Releases are triggered by pushing a tag. Nothing else publishes.

1. **Check the gate.** `main` must be green.

   ```bash
   gh run list --branch main --limit 1
   ```

2. **Bump the version** in `Cargo.toml`, `Cargo.lock` and `pom.xml`, on a branch:

   ```bash
   git switch -c chore/release-v1.1.0
   # edit Cargo.toml and pom.xml, then:
   cargo update --workspace
   git commit -s -m "chore(release): v1.1.0"
   gh pr create --repo Riptide-Labs/deltav-proto-contracts --base main
   ```

   `main` is protected, so this goes through a pull request like anything else. Merge once CI is green.

3. **Tag the merged bump commit.**

   ```bash
   git switch main && git pull
   git tag -a v1.1.0 -m "v1.1.0"
   git push origin v1.1.0
   ```

4. **Wait for the pipeline.** `release.yml` runs the same quality gates, then builds, signs, and creates a **draft** release with the artifacts attached.

   ```bash
   gh run watch
   ```

5. **Write the notes and publish.** Curate them: highlights, breaking changes with a migration path, then fixes. Do not paste a commit log.

   ```bash
   gh release edit v1.1.0 --notes-file notes.md --draft=false
   ```

Prerelease tags (`v1.1.0-rc1`) are marked `--prerelease` and must not be published as the latest release.

## What the pipeline produces

Attached to the GitHub Release:

| Artifact | What it is |
|---|---|
| `deltav-proto-contracts-<version>.jar` | Java stubs |
| `deltav-proto-contracts-<version>-sources.jar` | Java sources |
| `proto-<version>.tar.gz` | the raw `.proto` schemas |
| `sbom.spdx.json` | SPDX SBOM, generated by syft |
| `checksums.txt` | SHA-256 of every artifact above |
| `checksums.txt.sig`, `checksums.txt.pem` | cosign keyless signature and certificate |

SLSA build provenance is attested for each artifact and is verifiable with `gh attestation verify`.

## Verifying a release

**Checksums.** Download `checksums.txt` and the artifacts, then:

```bash
sha256sum --check checksums.txt
```

**Signature.** The checksums file is signed with cosign keyless, so verifying it covers every artifact it lists:

```bash
cosign verify-blob checksums.txt \
  --signature checksums.txt.sig \
  --certificate checksums.txt.pem \
  --certificate-identity-regexp '^https://github\.com/Riptide-Labs/deltav-proto-contracts/\.github/workflows/release\.yml@refs/tags/v.*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The identity regexp pins the signature to this repository's release workflow running on a version tag. A signature produced by any other workflow, repository or ref fails.

**Provenance.**

```bash
gh attestation verify deltav-proto-contracts-1.1.0.jar --repo Riptide-Labs/deltav-proto-contracts
```

## Preview builds

Every push to `main` refreshes a single rolling `preview` prerelease with artifacts built from that commit.
It is always marked as a prerelease, never carries a version tag, and is replaced by the next push.
Do not depend on it: use a released tag.

## Keeping this file honest

If the release pipeline changes, this file changes in the same pull request.
A `RELEASING.md` that describes a pipeline that no longer exists is worse than none.
